# Data provenance and task semantics

This page distinguishes third-party source data from the processed inputs used
in the revised EPSR experiments. It documents retained records to the extent
they permit verification; it is not a recipe for reproducing every paper table.
No raw or processed benchmark data are distributed in this repository.
Dataset licenses and terms remain those of their original providers; the
repository software license does not apply to third-party data. Provider terms
should be checked again at the time of acquisition.

## Belgium

- **Source and terms:** [Elia's historical measured/forecast total-load dataset](https://opendata.elia.be/explore/dataset/ods001/) supplies the Belgian grid load. The [Elia Open Data License](https://opendata.elia.be/pages/licence/) currently identifies CC BY 4.0. The retained processed benchmark covers 2023 at 15-minute resolution (35,040 rows). Historical meteorological covariates were obtained from the [Open-Meteo Historical Weather API](https://open-meteo.com/en/docs/historical-weather-api); Open-Meteo currently provides API data under CC BY 4.0 and applies separate service-use terms.
- **Processed schema:** `date, humidity, speed, mintem, temperature, maxtem, load`. `load` is the target; the five weather columns and historical load belong to the 96-row *encoder history*. Lag/rolling and historical calendar features are engineered from those rows. The target-time side receives an eight-value calendar vector only: cyclical hour, weekday and month, weekend flag, and peak-hour flag. No target-time load or meteorological observation is used.
- **Task/split:** past 96 quarter-hour rows → one scalar target at H1, H4, H24 or H96 rows after the last history row. H96 means 24 hours. Chronological train/validation/test division is applied after feature engineering; 6,874 aligned test targets per horizon.
- **Recovery limit:** the retained files do not establish all original Open-Meteo node coordinates, temporal interpolation and spatial aggregation settings. The published API alone is therefore insufficient to recreate the exact processed weather values. The local processed benchmark remains private; independently acquired data need not match its byte hash.

## Spain

- **Identified source:** Kaggle's [Hourly energy demand generation and weather](https://www.kaggle.com/datasets/nicholasjhana/energy-consumption-generation-prices-and-weather), dataset ID `nicholasjhana/energy-consumption-generation-prices-and-weather`. Kaggle identifies the source load/generation provider as ENTSO-E and the source weather as OpenWeather data for Valencia, Madrid, Bilbao, Barcelona and Seville. The Kaggle metadata currently labels the dataset `CC0: Public Domain`; consult the provider's current terms before acquiring or reusing it.
- **Source-to-input chain:** local source-shaped `Spain.csv` (`time`, `total load actual`, other power/price fields; 35,064 rows) and `spain_weather.csv` (`dt_iso`, `city_name`, temperature, humidity, wind and other fields; 178,396 city-hour rows) feed the retained preprocessing script. It converts timestamps to UTC, averages the selected five city-level weather values at each UTC timestamp, inner-joins weather to `total load actual`, converts selected temperatures from Kelvin to Celsius, and drops incomplete joined rows. Pressure and cloud cover appear in the source inventory but are **not** in the processed model input.
- **Processed input:** 35,028 rows, seven columns `date, humidity, speed, mintem, temperature, maxtem, load`, from `2014-12-31 23:00:00+00:00` through `2018-12-31 22:00:00+00:00`. It is *not* a perfectly continuous 35,064-row hourly series: 22 adjacent intervals exceed one hour. The five weather columns and load are available to the historical encoder; the target-time input is calendar-only. The model builds lag/rolling features from the processed series.
- **Task/split:** chronological 60/20/20 model protocol; past 96 processed rows → scalar `load` at H1/H4/H24/H96 row offset. Sampling is hourly where adjacent rows exist, so H96 is nominally 96 hours. The retained test set has 6,872 aligned targets per horizon. The timestamp conversion and dropped rows mean one should not infer an exact 96-hour elapsed lead across every irregularity.
- **Redistribution:** acquire source files from Kaggle; neither the local raw copies nor the processed benchmark are redistributed here. The source ID and processing code are supported by retained local artifacts, but a byte-exact original Kaggle download manifest was not preserved.

## London

- **Identified source:** Kaggle's [Smart meters in London](https://www.kaggle.com/datasets/jeanmidev/smart-meters-in-london), dataset ID `jeanmidev/smart-meters-in-london`, is a restructured release of smart-meter data from the [UK Power Networks Low Carbon London project](https://innovation.ukpowernetworks.co.uk/projects/low-carbon-london). Its source description reports 5,567 households, half-hourly `energy(kWh/hh)` readings, and an added `weather_hourly_darksky.csv` archive. Kaggle currently labels licensing `Database: Open Database, Contents: © Original Authors`; redistribution rights for derived copies are not established here.
- **Source-to-input chain actually retained:** the local `halfhourly_dataset/block_*.csv` files provide `LCLid, tstp, energy(kWh/hh)`. Invalid or missing energy readings are discarded. At each half-hour, the retained producer divides aggregate valid energy by the number of households reporting, multiplies that mean by a fixed population scale of **5,000**, and sums the available half-hour energy intervals within each hourly bin. It then restricts the result to 2012-01-01 through 2013-12-31. The producer applies no `>98%` meter-availability threshold and does not directly sum all households. The hourly profile is joined on timestamp to retained archived Dark Sky `temperature`, `humidity` and `windSpeed`; within-day temperature minima/maxima are derived and repeated. The inner join yields the final seven-column file.
- **Processed input:** 17,542 rows, `date, humidity, speed, mintem, temperature, maxtem, load`, from `2012-01-01 00:00:00` through `2013-12-31 23:00:00`. The load-only hourly file has 17,544 timestamps. The archived weather file lacks `2013-09-09 23:00:00` and `2013-09-10 00:00:00`; the join drops exactly those two rows. Thus the final series jumps from `2013-09-09 22:00:00` to `2013-09-10 01:00:00`: a **three-hour processed gap caused by missing weather**, not a missing raw load interval. The gap is preserved, not reindexed or imputed.
- **Task/split:** chronological 60/20/20 model protocol; past 96 processed rows → one scalar `load` at H1/H4/H24/H96 row offset, 3,374 aligned test targets per horizon. These are row-index horizons nominally 1/4/24/96 hours. Pairs crossing the preserved gap have a two-hour longer elapsed lead than the row count suggests.
- **Unit:** the target is in the native processed aggregate-demand units, kWh per hourly interval. Because one-hour energy in kWh is numerically equal to interval-average power in kW, the values also have a kW-equivalent numerical scale. The retained producer contains no division by 1,000 or other verified conversion to MW. Treat London as a fixed-scale aggregated household-demand benchmark constructed from real Low Carbon London observations, not as measured Greater London regional load.
- **Redistribution:** acquire original files from their providers. No London meter, weather or processed CSV is shipped here. The older `>98%` filtering and “raw load gap” descriptions are not supported by the retained current-file production chain.
